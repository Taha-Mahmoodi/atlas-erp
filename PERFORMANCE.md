# PERFORMANCE.md — Performance & Deployment-Cost Protocol (Mid-Build Addendum)

You are receiving this addendum while the build is in progress. Integration procedure, do this FIRST:
1. Commit this file at the repo root. Add to CLAUDE.md: "All code MUST comply with PERFORMANCE.md. Re-read it after any compaction."
2. Add every requirement below as numbered tasks in PLAN.md. For code that already exists (core, journal engine, FX), add explicit **retrofit tasks** ("audit fin_journal_* indexes against PERFORMANCE §1", "add pagination + query-count test to existing journal list endpoint"). File a `tech-debt` issue per GITHUB-WORKFLOW.md §6 for each retrofit found non-compliant.
3. From now on, the Definition of Done for any endpoint includes the checklist in §6.

Target: the entire system must run well for a 50-concurrent-user SME tenant on a single 4 vCPU / 8 GB VPS, with p95 latency under the budgets in §5 against the high-volume seed tenant.

# 1. Database & Indexing
- Every foreign key column gets an index. No exceptions. Alembic migrations that add an FK without its index fail review.
- Every column used in a WHERE filter, ORDER BY, or JOIN in any list/report endpoint gets an index; composite indexes for the dominant filter combination (e.g., `(tenant_id, posting_date)` on journal lines, `(tenant_id, item_id, warehouse_id)` on stock moves). `tenant_id` leads every composite index since every query filters on it.
- Aggregations for dashboards/reports never scan unbounded history at request time: date-bounded queries with covering indexes, or (for the cash/AR/AP KPI cards) small per-tenant summary tables maintained by event handlers — pick per case and record the choice in DECISIONS.md.
- All money math in `Decimal`/NUMERIC end to end. No floats anywhere in financial paths (this is correctness, but float-to-decimal retrofits are also expensive — enforce now).
- Use `EXPLAIN` during development on the three heaviest queries per module against the high-volume tenant; paste the plan summary into the PR description's Design notes.

# 2. Query Patterns (the N+1 ban)
- List endpoints execute O(1) queries, never O(n): explicit `selectinload`/`joinedload` for every relationship the response schema touches. Lazy-loading inside a response serialization loop is a `severity:major` bug.
- Enforce mechanically: a pytest fixture that counts SQL statements per request (SQLAlchemy event listener); every list-endpoint test asserts `query_count <= 3`. Add this fixture to tests/conftest.py as a retrofit task and apply it to existing endpoints.
- Bulk operations (MRP runs, payment runs, depreciation runs, seed loading) use bulk inserts/updates and set-based SQL, never per-row ORM loops over large sets.
- No SELECT *: load only the columns the schema needs on hot list endpoints (use `load_only` where models are wide).

# 3. API Behavior
- Pagination is mandatory on every collection endpoint — cursor-based, default page size 50, hard max 200. An unpaginated list endpoint may not merge.
- Report endpoints accept and require date-range bounds; the report builder caps result rows (10k) and offers CSV export for anything larger, generated by streaming, not by materializing in memory.
- Responses gzip-compressed (middleware); ETag/If-None-Match on slow-changing reference data (COA, item master, settings).
- Long-running operations (MRP, payment runs, statement imports over 1k lines) execute as background jobs returning a job id + polling endpoint, never inside a request that can hit a proxy timeout.

# 4. Frontend Discipline
- One screen = ideally one, max three API calls on initial render. Compose data server-side in purpose-built read endpoints rather than letting the UI stitch six requests.
- Data grid is virtualized (windowed rendering) — it must handle a 200-row page without DOM bloat.
- TanStack Query defaults: 30s staleTime on reference data, request deduplication on, no refetch storms on window focus for heavy reports.
- Route-level code splitting per module so the initial bundle stays small; production build target < 300 kB gzipped for the entry chunk.

# 5. High-Volume Seed Tenant + Latency Budget Tests
- Extend seed.py with a `--volume` tenant: ≥100k journal lines, ≥50k stock moves, ≥10k orders, ≥5k items, 3 fiscal years — generated with bulk inserts (seeding itself must finish in minutes, which also proves §2 bulk patterns).
- Add `tests/perf/` (marked `@pytest.mark.perf`, run in CI as a separate non-blocking job against SQLite, and locally against Postgres before each promotion): journal list w/ filters, trial balance, P&L, AR aging, stock-on-hand, order list — each asserts a wall-clock budget. Budgets against the volume tenant on Postgres: list endpoints p95 < 300 ms, statements/aging < 1.5 s, dashboard < 500 ms. Tune the SQLite CI numbers to be a looser smoke (2× budget) so CI stays stable while still catching regressions.
- A perf test failure before promotion is treated as `severity:major`: file the issue, fix or consciously re-budget with rationale in DECISIONS.md — never delete the test.

# 7. Deployment Doc (add docs/deployment.md before v1 promotion)
- Reference single-VPS topology: nginx/Caddy serving the static frontend build + reverse-proxying FastAPI (uvicorn, 2× vCPU workers) + Postgres on the same box; docker-compose.prod.yml with resource limits and Postgres tuned (shared_buffers 2 GB, work_mem sane, autovacuum on).
- Sizing table: demo/eval = 1 vCPU/2 GB; SME ≤50 users = 4 vCPU/8 GB; ≤200 users = 8 vCPU/16 GB or split DB onto its own box. State plainly that the app tier is stateless (JWT) so horizontal scaling is "add a container behind the proxy."
- Backup section: nightly `pg_dump` + WAL archiving note; restore drill instructions.
- A short "why it stays fast" section pointing at §1–§3 so operators understand the guarantees.
