# Maintenance (`backend/app/modules/maintenance/`)

Maintenance is the **seventh business module** (PLAN 9.2), the **Plant-Maintenance (PM)** half of the
parity QM/PM area, sitting **above finance** in the dependency order (STRUCTURE §5 / **D-051**). It is
the deliberately small PM core the [parity doc](../research/s4hana-parity.md) scopes: an **equipment
register**, **corrective** maintenance orders (created ad-hoc against a piece of equipment), and
**preventive** maintenance via interval-based **plans** that GENERATE due orders on a periodic run.
Everything else PM (functional-location hierarchies, maintenance notifications, measurement
points/counters, task lists, and counter/strategy-based scheduling) is **out of v1** — recorded in
the parity doc.

The normative design lives in [docs/architecture.md](../architecture.md) (D-012 docflow/numbering,
D-013 idempotency, D-029 opaque cross-module ids, D-015 money types, D-035 conditional GETs) and the
**D-051** decision in [DECISIONS.md](../../DECISIONS.md); this guide is the operator/contributor map.

## The three entities

### Equipment (`pm_equipment`)

A flat register of machines/vehicles/assets. `code` is **user-supplied** and unique per tenant (the
master-data precedent — no auto-number). `status` is `ACTIVE | INACTIVE | RETIRED`. `location` is a
**free-text label** (e.g. "Plant A / Line 3") — **not** a functional-location hierarchy (out of v1).
`cost_center_id` is an **opaque finance cost-centre id** (nullable, validated via
`finance/queries.cost_center_exists` when set — D-029, never a cross-module FK) for cost attribution.

### Maintenance order (`pm_maintenance_orders`)

A posted document (registers in `core_documents`, claims a gapless **`MNT-`** number at creation — the
production-order precedent). The prefix is `MNT-`, **not** `MO-` (already manufacturing's
production-order prefix). `order_type` is:

- **CORRECTIVE** — created ad-hoc against ACTIVE equipment (a breakdown/repair). No plan link.
- **PREVENTIVE** — generated by a plan's run; carries `maintenance_plan_id` + a plan→order docflow
  edge.

Lifecycle (`MaintenanceOrderStatus`): **DRAFT** (corrective, no schedule yet) → **SCHEDULED** (a
preventive order is born here) → **IN_PROGRESS** → **COMPLETED** (terminal; records `actual_cost` +
`completed_date`); any non-terminal state → **CANCELLED** (terminal). A corrective order can only
target **ACTIVE** equipment (an INACTIVE/RETIRED unit is rejected 422).

### Maintenance plan (`pm_maintenance_plans`)

An interval-based preventive task on a piece of equipment. `code` is user-supplied + unique.
`interval_value × interval_unit` (`DAYS | WEEKS | MONTHS`) is the recurrence. `next_due_date` is when
the next order is due; `last_generated_date` is the scheduled date of the last generated order
(`NULL` until the first generation). The plan also registers a `core_documents` row so it can be the
docflow **predecessor** of the orders it generates (the only master here that is a docflow source).
Status is `ACTIVE | INACTIVE` (an INACTIVE plan is skipped by the run).

## The interval model + generation run

At create, the first `next_due_date = start_date (or today) + one interval`. `MONTHS` uses calendar
arithmetic clamped to the month's last valid day (Jan 31 + 1 month = Feb 28). Changing a plan's
interval applies to the **next** advance — it does **not** retro-shift the current `next_due_date`.

`POST /maintenance-plans/run-preventive?as_of=<date>` (default today) runs the generator:

1. **Set-based scan** (`queries.due_plans`, PERFORMANCE §2): ONE query returns every ACTIVE plan with
   `next_due_date <= as_of`, ordered by code — no per-plan N+1 inside the scan.
2. Per due plan: create ONE PREVENTIVE order (SCHEDULED, scheduled at the plan's **current**
   `next_due_date`), write the plan→`generates`→order docflow edge, set `last_generated_date` = that
   due date, and advance `next_due_date`.

### The overdue-advance rule (D-051)

A plan overdue by **multiple** intervals generates exactly **ONE** order and advances `next_due_date`
forward by whole intervals until it is **strictly after** `as_of`
(*generate-one-advance-to-next-future*). This avoids order spam when a plan was missed for several
cycles while keeping the schedule on cadence. Example: a weekly plan with `next_due = 2026-01-08` run
at `2026-02-15` generates one order dated 2026-01-08 and advances `next_due` to 2026-02-19 (the next
weekly step after the run date).

### Idempotency

The run is **idempotent** two ways: the endpoint is D-013 idempotent (an `Idempotency-Key` replay
returns the captured result), and it is **naturally** idempotent — after a plan generates, its
`next_due_date` is strictly `> as_of`, so a same-day re-run finds nothing due and generates nothing.

### Inline vs job (D-032)

The run executes **inline** at v1 scale — the same call the 6.4 reorder-scan made (a tenant has tens,
not thousands, of plans; the scan is one query + a bounded per-plan order create). A background job
(the D-032 runner) is the documented later if plan counts grow.

## v1 cost handling: record-only (no GL posting)

Completing an order records `actual_cost` **on the order row** — there is **no GL posting** in v1.
The parity scope is "equipment register + corrective/preventive orders", **not** full work-order
costing. A maintenance-expense journal (Dr maintenance-expense / Cr a clearing or accrual, optionally
through the equipment's cost centre) is a **documented later**, wired via an event the way other
modules post through the bus. Keeping v1 record-only mirrors the parity posture (PM→FI integration is
not required for the minimal core) and avoids over-building. `estimated_cost` (on the plan and the
order) and `actual_cost` (on the order) are the figures a later costing phase would post from.

## Permissions (D-009)

`maintenance.equipment.read/.manage`, `maintenance.order.read/.manage/.complete`,
`maintenance.plan.read/.manage/.run`. `order.complete` is distinct from `order.manage` because it
records the actual cost (the value-bearing transition — the `journal.post` precedent); `plan.run` is
distinct from `plan.manage` for segregation of duties (running the generator vs authoring a plan).

## Cross-module boundary (STRUCTURE §5)

The only downward read is `finance/queries.cost_center_exists` (an equipment's optional cost centre).
No module imports maintenance yet; `maintenance/queries.py` is the only file a later module may import.
No cycle: finance is older and imports nothing from maintenance.

## What's out of scope (parity)

Functional-location hierarchies, maintenance notifications (v1 creates corrective orders directly,
losing the notification/request stage and MTBF/MTTR analysis), measurement points/counters,
counter/performance/strategy-based scheduling, task lists, and spare-part stock issue from a
maintenance order. Each is recorded as a "later" in the [parity doc](../research/s4hana-parity.md).
